# 通用微信聊天记录数据预处理方案

> 状态：设计稿
>
> 适用范围：经合法授权的微信聊天导出数据，用于对话回复型监督微调（SFT）、角色风格 LoRA、关系记忆 RAG 或相关数据分析。
>
> 重要边界：本文只描述通用处理方法，不包含真实联系人、微信号、真实聊天正文、真实样本、具体导出路径或任何特定人物的训练配置。

## 1. 目标与非目标

### 1.1 目标

建立一个可重复、可审计、可撤回的聊天数据处理流水线，将合法导出的微信数据转换为：

1. 统一的标准化消息数据；
2. 脱敏后的会话数据；
3. 可供人工审核的对话回复候选；
4. 按完整 session 切分的 SFT 数据集；
5. 可独立更新和删除的记忆候选数据；
6. 描述来源、处理规则、数据切分和质量结果的 manifest 与报告。

流水线必须支持从任一已完成阶段恢复，不修改原始导出，不覆盖已有数据集，不将未经授权的原始内容上传到外部服务。

### 1.2 非目标

本方案不包含：

- 破解、绕过或解析受保护的微信数据库；
- 自动登录微信、自动发消息或代替真人维持关系；
- 从零预训练基础语言模型；
- 首轮直接进行图片、视频、语音的多模态训练；
- 自动将训练结果发布为生产模型；
- 使用随机单消息切分替代 session 级数据切分；
- 通过提示词代替代码实现权限、授权、删除和质量控制。

## 2. 数据治理前置条件

处理真实聊天之前，必须建立授权记录。授权至少应明确：

- 数据主体和授权范围；
- 使用目的，例如风格学习、回复生成、记忆检索或评估；
- 允许处理的消息类型和媒体类型；
- 保存位置、可见范围和保留期限；
- 撤回授权的标识、流程和生效时间；
- 是否允许学习目标角色的语言风格；
- 是否允许处理第三方内容；
- 是否允许语音、图片、视频、文件和定位进入派生数据。

聊天授权、目标角色风格授权和媒体授权必须分别记录。任一授权缺失时，相应数据不得进入后续阶段。

原始数据、身份映射、未脱敏中间文件和私人模型工件只允许保存在受控本地存储中。Git、公开制品库、第三方在线模型、公共数据集和日志中不得出现原始聊天正文、真实身份标识或敏感媒体。

## 3. 总体处理流程

```text
合法导出
    |
    v
输入发现与完整性校验
    |
    v
格式导入适配器
    |
    v
标准化消息 JSONL
    |
    v
脱敏、过滤与媒体策略
    |
    v
发送者归一化、连续消息合并与 session 切分
    |
    +------------------------------+
    |                              |
    v                              v
回复候选生成与去重                 记忆/事件候选提取
    |
    v
人工审核与修改
    |
    v
按完整 session 进行时间切分
    |
    +------------------------------+
    |                              |
    v                              v
SFT JSONL                         RAG 记忆候选
    |
    v
质量、隐私、泄漏与血缘报告
```

每个阶段都应输出版本化产物、统计摘要、处理配置哈希和上游输入哈希。阶段产物采用追加式目录，不通过覆盖文件表达新版本。

## 4. 输入与统一导入接口

### 4.1 支持的输入

统一 importer 接口至少支持：

- 合法导出的 JSON；
- 结构化 CSV；
- 带时间、发送者和正文的 TXT；
- 可解析的 HTML 导出。

不同格式的字段差异必须在 importer 内解决，后续阶段只依赖统一消息接口。

无法合法获得明文的加密数据库不进入本流水线。遇到不支持的格式时，流程应生成可读错误报告并停止，不应猜测字段含义或静默丢弃消息。

### 4.2 流式处理要求

对于大型 JSON 或其他大文件，不应一次性加载完整消息集合。导入器必须支持流式读取或分块解析，并逐条写入标准化 JSONL。阶段之间以 JSONL、分区文件或其他可流式读取的格式传递数据。

流式处理必须保持：

- 原始顺序；
- 消息 ID；
- 解析错误的定位信息；
- 可恢复的偏移或分区信息；
- 对完整输入文件的哈希记录。

### 4.3 统一消息结构

内部标准化消息至少包含以下字段：

```json
{
    "message_id": "<stable_message_id>",
    "source_file": "<relative_source_file>",
    "source_record_index": 0,
    "timestamp": "<normalized_timestamp>",
    "speaker_id": "<speaker_id>",
    "speaker_role": "self|target|other|unknown",
    "message_kind": "text|emoji|image|voice|video|file|quote|link|system|payment|call|other",
    "text_original_ref": "<restricted_reference_or_null>",
    "text_redacted": "<redacted_text_or_null>",
    "media_refs": [],
    "reply_to": null,
    "source_hash": "<content_hash>",
    "parse_status": "ok|partial|failed"
}
```

真实姓名、微信号和原始正文只能保留在受控中间层的引用或加密映射中。进入人工审核、SFT、RAG 或报告的内容只能使用归一化角色名和脱敏正文。

## 5. 配置契约

处理逻辑必须由配置驱动，不能将目标联系人、目标角色、时间范围、路径、敏感字段或具体过滤规则写死在代码中。

配置至少包含：

```yaml
source:
    path: <authorized_input>
    format: auto
    timezone: <timezone>

speakers:
    self_id: <self_identifier>
    target_id: <target_identifier>
    unknown_policy: exclude

task:
    mode: conversational_sft
    target_role: target
    context_turns: 8
    context_max_chars: 1200
    assistant_only_loss: true

privacy:
    consent_scope: <consent_scope>
    redaction_version: <redaction_version>
    remove_contact_info: true
    remove_credentials: true
    remove_precise_location: true
    remove_third_party_private_data: true
    media_policy: semantic_placeholder_only

filter:
    exclude_kinds: [system, payment, call, file]
    exclude_recalled: true
    exclude_empty_and_null: true
    max_target_chars: 300
    max_target_chars_for_manual_review: 1000
    min_context_messages: 1

session:
    inactivity_gap_minutes: 120
    max_duration_minutes: 720
    max_context_turns: 8

candidate:
    target_count: 5000
    allow_short_replies: true
    near_duplicate_threshold: <threshold>

split:
    strategy: chronological_session
    train_ratio: 0.80
    validation_ratio: 0.10
    test_ratio: 0.10
```

配置本身不得包含密码、令牌、对象存储密钥或其他凭据。运行时应记录配置文件哈希和解析后的只读快照。

## 6. 标准化处理

### 6.1 时间与顺序

- 将时间统一为带时区的标准格式；
- 按源序号和时间稳定排序；
- 检测逆序、重复时间和无法解析的时间；
- 不擅自修正无法证明的时间；
- 对修正或丢弃的记录写入报告。

### 6.2 发送者归一化

将发送者映射到配置声明的角色：

```text
self       = 数据拥有者
target     = 目标角色
other      = 已知但不参与目标对话的发送者
unknown    = 无法可靠映射的发送者
```

`unknown` 默认排除出 SFT。`other` 的消息只有在获得授权且确实属于上下文时才能保留；群聊转发或第三方聊天记录默认视为独立内容，不得混入双人对话上下文。

### 6.3 文本规范化

统一换行、空白、Unicode 形式和不可见控制字符，但不得改变原始语义。原始正文与规范化正文必须分别保留引用关系和哈希。

### 6.4 连续消息合并

微信对话中同一发送者可能在极短时间内连续发送多个消息。构造训练 turn 前，应按以下条件合并：

- 同一 session；
- 同一发送者；
- 相邻消息间隔低于配置阈值；
- 消息之间没有明确的引用、媒体或主题边界。

合并后保留每条原始消息 ID 的列表，目标回复以合并后的完整 turn 作为标签。不能把连续碎片默认视为多个独立 assistant 回复。

## 7. 隐私脱敏与敏感内容处理

### 7.1 脱敏原则

脱敏应在进入候选和人工审核前完成，并同时作用于上下文和目标回复。替换优先于无理由删除，以保留必要的语言结构；替换标签必须稳定、可测试、可版本化。

脱敏类别至少覆盖：

- 电话、邮箱和其他联系方式；
- 身份证件、银行卡和支付标识；
- 密码、验证码、令牌和私钥；
- 精确住址、坐标和行程细节；
- 账号、内部链接参数和可追踪标识；
- 第三方姓名、联系方式和私密描述；
- 公司内部信息、客户信息和未公开材料。

推荐使用统一类别标记，例如 `<PII_CONTACT>`、`<SECRET>`、`<PRIVATE_LOCATION>`。不要把真实值保存在训练 JSONL、审核导出或模型评估输出中。

### 7.2 检测层级

脱敏至少包括：

1. 规则和正则识别；
2. 本地实体识别或分类器辅助识别；
3. 人工复核；
4. 脱敏后的二次扫描。

不能仅凭一次正则命中就宣称“无隐私泄漏”。误报和漏报都要记录统计。

### 7.3 高风险内容

以下内容默认不进入 SFT：

- 支付、转账、红包和原始支付 XML；
- 一次性口令、验证码、密码和访问令牌；
- 未经单独授权的照片、视频、语音、文件和定位；
- 第三方聊天原文或转发聊天记录；
- 明确要求不复现的争吵、秘密和私人事实；
- 无法完成脱敏或上下文解释的内容。

被排除的消息可以在受控的质量报告中仅以计数和类别出现，不输出原文。

## 8. 消息类型与媒体策略

首轮文本 SFT 只处理文本和有限的语义化表情。消息类型策略必须显式配置：

| 消息类型 | 首轮 SFT 默认策略 | 说明 |
| --- | --- | --- |
| 文本 | 候选来源 | 需通过脱敏、上下文和质量审核 |
| 普通表情 | 语义标签 | 不训练 GIF 或图片像素 |
| 图片 | 占位或排除 | 没有可靠文字描述时不作为目标回复依据 |
| 视频 | 排除 | 缩略图不能替代视频语义 |
| 语音 | 排除 | 没有经授权且经审核的转写时不使用 |
| 文件 | 排除 | 文件名和内容可能含有隐私或秘密 |
| 引用 | 解析后处理 | 分离被引用内容与当前回复 |
| 链接卡片 | 摘要或排除 | 去除追踪参数，不自动抓取外部网页 |
| 系统/通话/支付 | 排除 | 不属于角色对话目标 |

语义化表情应使用有限、稳定的类别集合。未知或无法可靠映射的表情保留为通用占位，不能让模型依赖某个媒体文件路径。

## 9. 过滤、异常与去重

### 9.1 自动过滤

自动排除或标记：

- 空文本、字面量空值和解析失败消息；
- 纯系统通知、通话状态和支付结构；
- 没有可用上下文的孤立目标回复；
- 只有媒体占位且没有授权文字描述的样本；
- 无法脱敏的高风险内容；
- 超出长度上限的异常消息；
- 无法映射的发送者。

过滤结果必须区分 `excluded` 和 `needs_review`，不能把人工待定项静默删除。

### 9.2 短回复处理

不能删除所有短回复。“确认”“附和”“调侃”和语气词是聊天风格的一部分，但需要控制短回复的总比例，并保证训练集仍包含足够的长短混合和上下文变化。

短回复应附带功能标签，例如确认、结束话题、情绪回应、追问或无意义重复。标签可用于抽样平衡，不直接暴露给模型。

### 9.3 超长消息处理

目标回复超过人工复核阈值时进入审核队列。超过硬上限的内容默认排除，除非人工确认其语义完整且没有不应复现的隐私。不得简单截断目标回复后直接作为训练标签；需要截断时必须按语义边界重新审核。

### 9.4 重复与近重复

去重分为：

- 消息 ID 重复；
- 完全相同文本；
- 规范化后相同文本；
- 近重复上下文和目标回复；
- 同一事件的重复导出。

最终样本只保留必要的一份，但 manifest 应保存重复组标识和被折叠记录数。近重复检测不能跨越 session 边界泄漏未来信息。

## 10. Session 切分

### 10.1 初始边界

先按标准化时间排序，以连续无消息间隔超过配置阈值作为新 session 的候选边界。该阈值只是初始规则，不代表所有主题边界。

### 10.2 辅助边界

还应考虑：

- 最大 session 时长；
- 长时间中断后的重新问候；
- 明显主题切换；
- 引用、转发或新事件开始；
- 连续媒体或系统消息造成的语义断点；
- 人工审核发现上下文不连贯。

session 过长时，应在保持语义完整的前提下生成多个窗口。窗口之间可以有上下文重叠，但同一窗口不能跨 split。

### 10.3 Session 质量要求

每个 session 至少保留：

- 稳定 session ID；
- 起止时间；
- 消息 ID 列表；
- 参与发送者角色；
- 上游标准化文件哈希；
- 切分规则版本；
- 人工修订记录（如有）。

## 11. 聊天回复候选构造

### 11.1 目标定义

对于目标角色的合格回复：

1. 只使用该回复之前、同一 session 内的消息作为上下文；
2. 目标角色当前回复是唯一 assistant 标签；
3. 另一方的消息和历史目标回复只作为上下文；
4. 目标回复之后的消息不能进入输入；
5. 没有足够上下文或严重依赖媒体时不生成候选。

### 11.2 上下文窗口

上下文应同时受以下约束：

- 最大消息轮数；
- 最大字符数或 token 数；
- session 边界；
- 主题连续性；
- 模型训练时的最大序列长度。

不能把整个历史会话无条件拼接到每条样本。窗口截断应优先保留最近的完整轮次，不能截断一条消息到不可解释的半句。

### 11.3 训练消息结构

内部 SFT 样本采用角色化消息结构：

```json
{
    "sample_id": "<session_id>_<turn_id>",
    "messages": [
        {"role": "system", "content": "<product_boundary_prompt>"},
        {"role": "user", "content": "<serialized_context>"},
        {"role": "assistant", "content": "<target_reply>"}
    ],
    "metadata": {
        "source_session_id": "<session_id>",
        "source_message_ids": ["<message_id>"],
        "target_speaker": "target",
        "consent_scope": "<consent_scope>",
        "redaction_version": "<redaction_version>",
        "review_status": "keep|redact_keep",
        "split": "train|validation|test"
    }
}
```

训练实现必须支持 assistant-only loss。system 消息用于产品边界，LoRA 主要学习语言风格和回复行为，不应承担事实记忆、权限判断或真人身份冒充。

## 12. 候选排序与人工审核

### 12.1 机器候选生成

机器初筛用于缩小审核范围，不用于自动决定最终训练集。候选分数可以综合：

- 上下文完整度；
- 目标回复可读性；
- 双方轮次平衡；
- 主题多样性；
- 回复长度多样性；
- 互动行为类型多样性；
- 脱敏通过情况；
- 媒体和系统消息依赖程度；
- 完全或近重复惩罚；
- 敏感度风险。

候选生成应先从全部合格目标回复中得到较大的机器候选池，再通过去重、分层抽样和风险排序缩小到人工审核规模。候选池大小和审核预算由配置决定，不固定为某个联系人或某个数据集的数字。

### 12.2 审核页面

本地审核界面每次只展示脱敏数据，至少包括：

- session 和时间的非身份化标识；
- 最近若干轮上下文；
- 目标角色回复；
- 脱敏命中类别；
- 媒体、引用和链接标记；
- 机器筛选分数及原因；
- 原始消息 ID 的受控引用，而非原始身份信息。

审核界面不得向外部服务发送样本，不默认保存浏览器缓存或截图。

### 12.3 审核标签

至少支持：

```text
keep          直接保留
redact_keep   人工修改脱敏后保留
reject        排除
uncertain     暂不决定
```

`reject` 和 `uncertain` 应记录结构化原因，例如隐私风险、第三方内容、上下文不足、媒体依赖、重复、长度异常或质量不足。人工修改后的正文必须产生新的内容哈希和修改记录，不能覆盖原始中间层。

### 12.4 抽样平衡

最终样本从审核通过项中分层抽样，至少平衡：

- 时间阶段；
- session；
- 回复长度；
- 提问、安慰、调侃、分享、拒绝、结束话题等互动类型；
- 表情和语气词使用比例；
- 短回复与多句回复；
- 关系阶段或产品允许的边界标签。

不得为了达到目标条数而放宽隐私、泄漏或授权门禁。

## 13. 数据切分与防泄漏

### 13.1 切分单位

切分单位必须是完整 session 或完整语义窗口，不能按单条消息随机分配。训练、验证和测试之间不得共享 session、重复组或近重复上下文。

### 13.2 时间策略

默认使用按时间排序的切分：较早 session 用于训练，中间时间段用于验证，最新且冻结的时间段用于最终测试。比例只是初始配置，实际结果以 session 数量和样本质量报告为准。

### 13.3 未来信息检查

每条样本必须通过以下检查：

- 输入中不存在目标回复之后的消息；
- 输入中不存在来自未来时间段的事实摘要；
- 关系阶段标签不使用未来消息推断；
- 记忆候选的来源时间不晚于样本目标回复；
- 相同 source message 不出现在多个 split。

### 13.4 Manifest

每个 split 至少输出：

- session ID 列表；
- 样本 ID 列表；
- 内容和配置哈希；
- 时间范围；
- 样本数量与字符/token 统计；
- 近重复组统计；
- 泄漏检测结果。

### 13.5 挑战集接口

除按时间冻结的测试集外，流水线应预留独立的人工构造挑战集接口。挑战集不从训练集随机抽取，而是由授权审核者基于脱敏上下文和抽象场景标签构造，用于覆盖普通时间切分中可能不足的行为：

- 安慰、追问、调侃、拒绝和结束话题；
- 极短回复与多句回复；
- 长消息和连续消息合并后的回复；
- 表情语义标签和媒体占位；
- 关系阶段或互动边界变化；
- 不应猜测或复述的私人事实；
- 无相关记忆时的“不确定”回答。

挑战集只保存必要的脱敏上下文、目标行为标签、审核依据和版本信息，不复制未经授权的完整私人对话。它应独立冻结，不参与训练选参，并在每次模型比较中使用同一版本。

## 14. SFT 与 RAG 的职责分离

SFT/LoRA 只学习经过授权的语言风格、回复长度、语气和互动行为。以下内容原则上不作为风格权重的主要载体：

- 可更新的个人事实；
- 共同经历的详细原文；
- 高敏感关系信息；
- 实时天气、时间、位置或外部状态；
- 需要精确删除和审计的记忆。

这些内容应进入独立的记忆卡或事件卡，并保存来源 session ID、时间范围、敏感度、授权范围和删除状态。RAG 删除不能依赖重新过滤文本；必须能通过来源 ID 反向定位索引、缓存和模型工件。

## 15. 目录与产物约定

数据处理根目录应与源代码和训练项目分离。推荐使用以下抽象布局：

```text
<data_processing_root>/
├── configs/
│   └── wechat_preprocess.yaml
├── input/
│   └── <source_export>/
├── work/
│   └── <dataset_id>/
│       ├── 01_import/
│       ├── 02_normalized/
│       ├── 03_redacted/
│       ├── 04_sessions/
│       ├── 05_candidates/
│       └── 06_review/
├── output/
│   └── <dataset_id>/
│       ├── datasets/
│       │   ├── train.jsonl
│       │   ├── validation.jsonl
│       │   └── test.jsonl
│       ├── normalized/
│       ├── memories/
│       ├── manifests/
│       └── reports/
└── deletion-ledger/
```

源导出只读保存。`dataset_id` 应由源输入哈希、配置版本、脱敏版本、任务类型和目标角色配置的稳定摘要生成，避免不同处理版本互相覆盖。

每次运行至少输出：

```text
source_manifest.json
import_report.json
normalization_report.json
privacy_report.json
session_report.json
candidate_report.json
review_report.json
split_manifest.json
leakage_report.json
lineage.jsonl
quality_report.json
```

报告只包含计数、类别、哈希、规则版本和经过严格脱敏的摘要，不包含完整私聊正文、原始身份或未授权媒体。

## 16. 血缘、授权撤回与删除

每条派生记录都应保存：

- 上游文件或消息 ID；
- 上游内容哈希；
- 处理阶段和版本；
- 配置哈希；
- consent scope；
- 生成时间；
- 下游对象 ID。

删除流程按以下链路反向查找：

```text
授权范围
→ 原始文件/消息
→ 标准化消息
→ 脱敏消息
→ session
→ 候选与人工审核记录
→ SFT/RAG 数据集
→ 向量索引与缓存
→ 训练 run、checkpoint、adapter 和备份
```

LoRA 权重无法可靠地删除某一条训练样本的影响。若已撤回的数据进入 adapter，必须将受影响 adapter 标记为不可用，删除受控副本，并从清理后的数据重新训练。删除账本只保存对象标识、时间、范围和结果，不保存被删除的私密正文。

## 17. 质量门禁

进入训练前必须通过：

- 输入文件哈希和来源清单已记录；
- importer 解析错误已处理或明确豁免；
- 消息 ID 无重复，顺序检查通过；
- 未知发送者数量符合配置要求，SFT 中为零；
- 脱敏规则和二次扫描通过；
- 支付、口令、秘密和明确 PII 未进入训练集；
- 媒体缺失不会生成伪造文本；
- 连续消息合并和 session 切分结果可追溯；
- assistant 标签全部来自目标角色；
- 输入不包含目标回复之后的消息；
- train/validation/test 无 session、重复组和近重复交叉；
- 人工审核状态和拒绝原因完整；
- 每条样本可追溯至源消息；
- RAG 候选有授权范围和来源 session；
- 删除指定 consent scope 时能列出全部受影响派生物。

未通过任一硬门禁时，数据只能作为待处理工件保存，不得启动正式 LoRA 训练或发布模型。

## 18. 测试与验收

### 18.1 单元测试

至少覆盖：

- 各输入格式的 importer；
- 时间标准化与稳定排序；
- 发送者映射；
- 连续消息合并；
- 表情语义化；
- PII、口令和秘密脱敏；
- 引用与媒体处理；
- session 边界；
- 完全和近重复检测；
- assistant-only loss 所需的消息结构；
- split 泄漏检测；
- manifest 和 lineage 生成。

### 18.2 小规模验证

在处理完整数据前，使用受控的小型 fixture 验证：

- 导入结果与预期字段一致；
- 中断后可从阶段产物恢复；
- 同一输入和配置得到相同 dataset digest；
- 修改脱敏规则会产生新的版本而不覆盖旧产物；
- 删除某个授权范围可以定位所有下游对象。

### 18.3 人工验收

人工抽查应覆盖不同时间阶段、session 长度、回复长度、互动类型和媒体依赖情况。抽查记录只保存审核结论和问题类别，不复制完整私人对话到报告或工单。

## 19. 实施顺序

推荐按以下顺序实现：

1. 定义统一消息接口、配置契约和 manifest；
2. 实现流式 importer 与完整性报告；
3. 实现标准化、角色映射和连续消息合并；
4. 实现脱敏、过滤、媒体策略和二次扫描；
5. 实现 session 切分、窗口构造和去重；
6. 实现候选生成、分层排序和本地审核；
7. 实现 session 级时间切分与泄漏检测；
8. 导出 SFT JSONL 和 RAG 记忆候选；
9. 补齐删除账本、恢复流程、测试和质量门禁。

在数据契约、授权范围、split 完整性和脱敏测试未通过前，不进入正式模型训练。首轮训练应使用少量人工审核通过的高质量样本验证 loss mask、保存加载和评估流程，再逐步扩大数据规模。

## 20. 设计结论

本方案将“聊天记录预处理”视为一个可审计的数据工程问题，而不是一次性清洗脚本。其关键原则是：

- 原始数据只读、派生数据版本化；
- 处理逻辑配置化、输入格式适配化；
- 机器负责缩小范围，人工负责最终取舍；
- 目标回复和上下文角色严格分离；
- 连续消息先合并，session 完整切分；
- 风格学习与事实记忆分离；
- 隐私、授权、删除和泄漏检查属于训练前置条件；
- 所有结果都能从派生样本回溯到授权来源。
