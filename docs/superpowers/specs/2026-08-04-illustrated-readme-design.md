# 图文版 README 重构设计

## 目标

把仓库根目录 `README.md` 从“技术说明中穿插图片”重构为“图解导览 + 技术手册”两层内容。
图片必须承担解释平台概念的作用，正文需要在图前建立问题、在图后解释视觉隐喻并给出工程含义，
不能只插入图片链接或重复图片中的文字。

重构不改变平台架构、部署方式、命令、端口、路径、安全边界或训练项目契约，也不新增平台能力。

## 目标读者

- 第一次进入仓库、需要快速理解平台边界的算法工程师和平台工程师。
- 准备接入新训练项目、需要理解可复现与可恢复要求的项目维护者。
- 已经熟悉平台、只需要查询部署命令、端口和运维文档的操作者。

## 信息架构

README 保留单文件结构，按阅读深度分成两层。

### 第一层：图解导览

前半部分使用四个连续的认知锚点：

1. **平台不是单一模型工程**
   - 使用一体化训练装置图。
   - 图前说明为何需要把开发、执行、治理和持久化连成一个平台。
   - 图后用简短列表解释 JupyterLab、Ray、MLflow、MinIO 如何共同产出可复现训练。
2. **组件协作形成可恢复闭环**
   - 使用小黑踩动训练闭环图。
   - 将原组件职责表保留为精确参考，在图片周围增加“谁负责什么、接口边界在哪里”的导读。
   - 明确客户端只经过 MLflow API，不直连后端数据库或 Artifact Bucket。
3. **训练结果必须可审计、可晋级**
   - 使用训练鼓图。
   - 将八个生命周期步骤归纳为数据身份、验证选参、干净重训、质量门禁四个阶段。
   - 保留完整八步清单作为展开细节，并突出测试集禁止回流和人工晋级。
4. **新项目是一套工程契约，不是一份 Notebook**
   - 使用训练项目箱图。
   - 图前介绍推荐目录，图后把目录与可复现、可测试、可恢复要求逐项对应。
   - 保留现有项目契约清单，不把可选目录误写成强制要求。

每个锚点采用统一节奏：核心判断 → 图片 → “图中表达什么” → 工程落地。说明文字控制在
一至两个短段落和三至五个要点，避免把图片变成重复配文。

### 第二层：技术手册

后半部分继续承载可检索的操作信息：

- 当前部署形态与数据持久化边界。
- 快速开始、服务健康检查和 MLflow 客户端配置。
- 服务端口、systemd 验证和网络安全要求。
- MLflow 实验分析、示例工作负载、仓库结构和验证命令。
- 文档索引、安全与持久化说明。

这部分以准确和便于复制为主，不为追求叙事感改写命令，也不把主机特定配置包装成通用默认值。

## 图片与文件约束

- 继续使用 `images/01-platform-integration.png` 至 `images/04-training-project-contract.png`。
- 不重新生成、不覆盖现有图片，也不增加装饰性配图。
- Markdown 使用相对路径，保证仓库在不同主机路径下检出时仍能渲染。
- 图片替代文本说明图的工程含义，不使用“图片 1”之类无信息描述。

## 编辑边界

- 允许调整章节顺序、标题层级、段落和列表，以改善图文节奏。
- 允许合并重复介绍，但必须保留所有平台职责、API 边界、训练门禁和安全要求。
- 不修改各子项目 README、部署文档、代码、服务配置或生成图片。
- 不处理工作区中与本任务无关的 `outputs/`。

## 验证

完成后执行以下检查：

1. README 中四张图片都存在，引用顺序与叙事顺序一致。
2. 所有相对文档链接和目录链接都能解析。
3. Markdown 标题层级、表格、代码围栏和列表结构完整。
4. `git diff --check` 无空白或补丁格式错误。
5. Git 变更范围只包含 README、四张图片和本设计说明，不包含 `outputs/` 或其他用户文件。
6. 逐项核对原 README 的命令、端口、路径、服务边界和安全规则没有丢失或改变。
