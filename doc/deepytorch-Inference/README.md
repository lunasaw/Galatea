# PyTorch 推理加速选型与验证规范

本文档用于指导 PyTorch 模型从正确性基线进入性能优化、候选选型、统一验证和生产发布。
它适用于通用模型、生成式模型、在线服务、离线批处理和端侧部署。技术状态核验日期为
**2026-08-11**；正式实施仍须按目标版本重新检查兼容矩阵和维护状态。

本规范只定义决策和验收方法，不承诺某个引擎在所有模型上最快。最终结论必须来自目标模型、
生产输入分布和目标硬件上的可复现实测。

## 1. 核心原则

1. **先测 PyTorch 单次推理基线**：训练产物冻结后，先回答原模型在目标硬件上一次推理多慢、
   占用多少资源，再讨论加速。
2. **相对收益与绝对 SLO 分开**：加速目标以基线改善幅度表达；质量、SLO、成本和资源是最终
   能否上线的绝对门槛。
3. **先保留基线，再引入优化**：始终保留可运行的 PyTorch eager 基线和上一生产版本。
4. **先定位瓶颈，再选工具**：编译器不能解决排队，服务框架也不能自动加速模型算子。
5. **硬门槛优先于评分**：兼容性、质量、安全或恢复性不合格，性能得分不能补偿。
6. **只比较 2 至 3 个候选**：先按场景和硬门槛收敛，再按同一协议做正式验证。
7. **优化组合必须重新验收**：编译、量化、批处理和缓存的收益不能简单相乘。
8. **构建、验证和发布可追溯**：数据、代码、环境、制品和结果统一关联 MLflow Run ID。
9. **生产变更必须可回滚**：压测脚本不得自动修改生产模型 alias。

## 2. 决策流程

```text
训练完成的模型 / MLflow Run
  -> 冻结权重、代码、前后处理和输入契约
  -> B0：PyTorch eager 单次推理基线
  -> B1：PyTorch eager 调优对照组
  -> 根据基线差距定义相对优化目标
  -> profiler 定位主要瓶颈
  -> 场景候选集
  -> 兼容性硬门槛
  -> 2~3 个 PoC
  -> 质量与性能统一验证
  -> 稳定性、故障和成本验证
  -> 加权评审
  -> 主方案 + 回滚方案
  -> 影子/灰度 + 显式发布审批
```

任何一步不满足门槛都应停止晋级并记录原因，而不是继续扩大压测规模。

## 3. 选型输入

选型负责人必须在测试前填写以下内容。缺少生产分布、质量门槛或目标硬件时，只能做探索性
实验，不能形成采购、容量或发布结论。

| 类别 | 必填内容 |
| --- | --- |
| 模型身份 | 项目、任务、架构、参数量、源 MLflow Run ID、权重和代码 revision/digest |
| 模型契约 | 输入输出 schema、dtype、shape/长度范围、自定义算子、前后处理、tokenizer/template |
| 基线记录 | B0/B1 Run ID、单次推理边界、输入点位、冷/热延迟、吞吐、内存/显存和质量 |
| 质量 | 主指标及方向、基线值、允许退化、关键切片、安全/业务规则、最终测试集边界 |
| 流量 | 在线/离线/流式/端侧、平均和峰值 QPS、并发、突发、batch、到达过程 |
| SLO | P50/P95/P99、超时、错误率、goodput、冷启动、恢复时间和可用性目标 |
| LLM 分布 | 输入/输出 token 联合分布、最大上下文、长请求比例、缓存命中、取消和慢客户端 |
| 硬件 | CPU/加速器型号与数量、内存/显存、拓扑、功耗模式、驱动和固件 |
| 运行环境 | OS、容器 digest、Python/PyTorch/运行时版本、Ray/Kubernetes/裸机、目标语言 |
| 资源和成本 | 每副本资源、节点上限、每请求/样本/百万 token 成本和功耗目标 |
| 组织约束 | 交付期限、维护能力、许可证、安全支持、闭源 runtime、厂商绑定和退出要求 |

输入范围应使用生产统计量表达，例如图像分辨率或序列长度的 P50、P95、P99、最大值和异常值，
不能用一个方便导出的示例输入代替。

## 4. 如何选择加速方案

### 4.1 从训练产物建立单次推理基线

模型训练结束并通过质量门槛后，先冻结权重、代码、前后处理、输入契约和目标硬件。未经这一步，
后续数字无法证明来自推理优化，而不是模型或数据变化。

建立两级 PyTorch 基线：

| 基线 | 固定配置 | 用途 |
| --- | --- | --- |
| B0：基础单次推理 | PyTorch eager、原始认可精度、`batch=1`、`concurrency=1`、无编译/量化/专用引擎 | 作为训练产物的统一质量、延迟和资源参考 |
| B1：调优 eager | 同一模型，加入合理线程/NUMA、数据搬运、内存格式、认可的 BF16/FP16 等基础优化 | 排除明显使用错误，公平判断编译器或引擎的增量贡献 |

B0 和 B1 均必须使用 `model.eval()` 与 `torch.inference_mode()`；这属于正确推理状态，不应被包装
成候选引擎的加速收益。B1 的每项变化单独记录，精度变化必须重新做质量验证。

单次推理至少分别测量以下边界：

1. **冷启动**：进程启动、模型/权重加载、设备初始化到第一个结果；
2. **热态模型执行**：输入已在目标设备，仅计算一次 forward/generate；
3. **热态本地端到端**：预处理、H2D、模型执行、D2H 和后处理；
4. **服务端到端**：只有进入服务阶段后再加入协议、序列化、排队和网络，不与纯模型数字混用。

`batch=1` 不能只测一个方便样例。固定输入集合并至少覆盖生产 P50、P95 和最大允许 shape/长度；
LLM 同时固定输入和输出 token 数。预热后测稳态，CUDA/ROCm 使用设备 event 或正确同步，同时
保留首请求结果。记录延迟分布、吞吐、CPU/RSS、设备峰值内存和质量，而不是只记一个平均值。

### 4.2 从基线定义优化目标

加速目标首先写成相对 B0/B1 的改善，而不是脱离基线指定一个“应该达到”的框架速度：

```text
latency_speedup       = baseline_latency / candidate_latency
latency_reduction     = 1 - candidate_latency / baseline_latency
throughput_gain       = candidate_throughput / baseline_throughput - 1
memory_reduction      = 1 - candidate_peak_memory / baseline_peak_memory
required_speedup      = baseline_latency / absolute_latency_slo
```

所有公式必须比较同一输入、精度、batch、并发、统计分位和计时边界。例如 B0 的热态 forward
P50 只能与候选的热态 forward P50 比；不能拿模型执行时间与 HTTP 端到端时间计算加速比。
若业务 SLO 是 HTTP 端到端延迟，`required_speedup` 必须使用对应的端到端基线，不能使用纯
forward 基线代入。

每个候选同时报告两组结果：相对 B0 的**端到端总收益**，以及相对“相同精度、相同基础配置”
B1 的**编译器/引擎增量收益**。这样可以区分收益来自 BF16/FP16、数据搬运、批处理，还是来自
`torch.compile`、TensorRT、ONNX Runtime 等引擎本身。没有逐步消融时，不宣称单项优化贡献。

相对优化目标应在 B0/B1 测量完成、候选结果揭晓前冻结。例如“相对 B1 的 P95 延迟降低至少
30%，峰值显存降低至少 20%，质量退化不超过 0.2 个百分点”。业务绝对门槛仍需独立判断：

- 基线未达到 SLO 时，以 `required_speedup` 加工程余量确定最低收益；
- 基线已经达到 SLO 时，只在成本、容量或硬件约束有明确收益时继续优化；
- 候选即使相对基线快很多但仍不满足绝对 SLO，也不能发布；
- 候选满足 SLO 但相对收益很小且显著增加维护成本，可以继续使用基础 PyTorch 方案。

示例：某模型在同一输入和硬件上的 B0 单次热态 P50 为 18.4 ms，B1 为 14.2 ms，TensorRT
候选为 8.1 ms。应报告“相对 B0 总加速 2.27x、相对 B1 引擎增量加速 1.75x”，而不是只写
“TensorRT 加速 2.27x”。若业务绝对门槛是 P50 小于 10 ms，该候选同时通过相对收益和绝对
门槛；若门槛是 5 ms，则仍不能发布。

### 4.3 按场景收敛候选

| 场景 | 必留基线 | 首批候选 | 主要判断点 |
| --- | --- | --- | --- |
| 通用 NVIDIA GPU | eager + FP32/BF16/FP16 | `torch.compile`、Torch-TensorRT/TensorRT；跨语言时 ORT | 算子覆盖、shape profile、fallback、engine 构建和 P99 |
| 通用 CPU | eager + 固定线程/NUMA | `torch.compile`、ONNX Runtime；Intel 加 OpenVINO | ISA、线程过订阅、batch、BF16/INT8 内核和内存带宽 |
| Intel GPU/NPU | PyTorch 支持路径 | OpenVINO、ORT 对应 EP | 目标设备支持、异构回退、量化格式和驱动版本 |
| NVIDIA LLM/VLM | Transformers BF16/FP16 | vLLM、SGLang；高性能上限加入 TensorRT-LLM | TTFT、ITL、KV 容量、连续批处理、多卡通信和量化质量 |
| AMD LLM/VLM | Transformers + ROCm | 目标版本明确支持的 vLLM、SGLang | GPU 型号、attention/量化 kernel、collective；不可套用 CUDA 结论 |
| CPU/桌面 LLM | Transformers CPU | llama.cpp、MLC LLM；需要标准接口时评估 ORT GenAI | 格式转换、量化质量、内存、包体和本地设备覆盖 |
| Apple/移动/嵌入式 | 设备原生或 PyTorch 开发基线 | ExecuTorch、ORT Mobile；Apple-only 加 Core ML | delegate 覆盖、包体、低端真机、温升、电量和系统 fallback |
| TPU/Inferentia/Ascend 等 | 厂商 PyTorch 前端 | 厂商编译器/runtime | 支持矩阵、制品绑定、算子迁移、成本和可退出性 |

`torch.compile` 通常是保留 PyTorch 语义时迁移成本最低的首个编译候选。ONNX Runtime 适合
跨语言或跨硬件交付；TensorRT 适合稳定的 NVIDIA 模型追求性能上限；OpenVINO 适合 Intel
平台。编译器团队才能长期维护的 TVM/IREE/自定义 kernel 不应进入普通项目的默认候选集。

### 4.4 精度和压缩方案

精度是引擎配置的一部分，不是独立排名。每种精度必须和最终运行时一起验证。

| 条件 | 建议起点 | 进入更激进方案的条件 |
| --- | --- | --- |
| 现代 GPU/CPU，质量敏感 | BF16；硬件不支持时 FP16 | 性能或容量仍不达标且存在受支持低精度内核 |
| CNN/Encoder | FP16/BF16，再评估 INT8 PTQ | 有代表性校准集；质量不通过再考虑 QAT |
| LLM 显存或带宽受限 | BF16/FP16，再评估 INT8/INT4 weight-only | 目标引擎直接支持权重布局、group size 和 kernel |
| 新一代加速器 | 受支持的 FP8/混合精度 | 固定缩放策略、硬件代际和软件兼容集合 |
| 极限压缩 | 蒸馏、结构化稀疏或更小架构 | 能重新训练并证明端到端收益和质量 |

低位宽不保证更快。缺少融合内核时，量化/反量化和布局转换可能抵消收益。量化校准和方案选择
只能使用训练集或验证集证据，不能反复查看最终测试集。

### 4.5 服务层单独选择

服务层负责协议、排队、批处理、副本、伸缩和故障恢复，不等于模型执行加速：

| 条件 | 服务候选 |
| --- | --- |
| 本仓库已有 Ray，需资源调度、DAG、在线/离线统一 | 优先 Ray Serve；底层仍独立选择引擎 |
| NVIDIA 多框架模型、统一 HTTP/gRPC 和模型仓库 | NVIDIA Triton Inference Server |
| 组织已有 Kubernetes 推理控制面 | KServe + 明确的实际 runtime |
| LLM PoC 或单引擎服务 | 先使用 vLLM/SGLang/TRT-LLM 自带 server，避免过早叠加队列 |
| 轻量单模型接口 | FastAPI/gRPC 适配器，但需自行补齐健康、背压、指标和发布能力 |

不要无条件叠加 Ray/Triton 动态批处理与 LLM continuous batching。双层队列常提高尾延迟并使
取消、背压和容量难以解释。

### 4.6 兼容性硬门槛

任一项为“否”且没有在交付期内可验证的修复路径时，候选淘汰：

| 门槛 | 通过条件 |
| --- | --- |
| 模型覆盖 | 关键算子、控制流、自定义 op、前后处理和输出结构均受支持 |
| 输入覆盖 | P50/P95/P99/最大 shape 或 token 范围可表达，无持续重编译或越界 |
| 硬件覆盖 | 目标型号、驱动、架构、多卡拓扑和低精度在官方支持矩阵内 |
| 质量 | 主指标、关键切片和业务/安全规则达到预设门槛 |
| 服务契约 | batch、流式、取消、超时、工具调用、错误语义和目标语言均满足 |
| 安全合规 | 许可证可接受，仍有安全修复，制品和插件来源可验证 |
| 可观测性 | 能识别 fallback、重编译、错误、资源、排队和关键 LLM 指标 |
| 可恢复性 | 可从源模型重建，健康检查、故障恢复和上一版本回滚已验证 |

禁止把“导出成功”当作覆盖通过。必须检查实际节点分配、分区边界、CPU/eager fallback、设备
复制和所有生产 shape。

### 4.7 通过硬门槛后的评分

评分采用 1 至 5 分，权重在测试前固定并纳入评审记录。默认权重如下：

| 维度 | 权重 | 必须使用的证据 |
| --- | ---: | --- |
| 质量与数值 | 20% | 正式质量集、关键切片、回归报告 |
| SLO 与 goodput | 20% | 生产分布负载测试，包含 P99 和过载点 |
| 资源与成本 | 15% | 峰值内存/显存、设备数、功耗和单位有效请求/token 成本 |
| 稳定性与恢复 | 15% | 长稳、OOM 边界、取消、进程/节点失败和回滚演练 |
| 工程复杂度 | 10% | 代码、plugin、构建、调试、发布和升级工时 |
| 覆盖与可移植性 | 10% | fallback/shape/硬件报告、标准格式和退出路径 |
| 运维、安全与维护 | 10% | 指标、告警、CVE 响应、许可证、release 和支持渠道 |

```text
总分 = sum(维度得分 / 5 * 维度权重)
```

总分只用于通过硬门槛的候选排序。决策记录还必须单列未知风险、未测范围、厂商绑定、自定义
plugin 和单人维护风险。若性能置信区间重叠且总分接近，优先选择工程复杂度和退出成本更低的
方案，不对噪声范围内的差异做过度解释。最终选择一个主方案和一个已验证的回滚方案。

## 5. 验证规范

### 5.1 六级验证门禁

| 门禁 | 验证内容 | 通过产物 |
| --- | --- | --- |
| V0 基线与可复现 | 固定源模型、代码、环境、数据/回放、构建参数和硬件；完成 B0/B1 | 基线报告、manifest、digest、构建脚本、MLflow Run ID |
| V1 功能与覆盖 | schema、正常/边界/错误输入、算子覆盖、fallback、所有 shape profile | 契约测试、覆盖/分区报告、失败样例 |
| V2 数值与质量 | 数值层、任务层、业务/安全层，含关键切片 | 质量报告和预先定义的门槛判定 |
| V3 离线性能 | 模型执行和端到端离线的延迟、吞吐、内存、启动和成本 | 原始聚合数据、环境、命令、性能曲线 |
| V4 服务与可靠性 | 真实到达过程、SLO 容量、过载、长稳、取消和故障恢复 | 负载、长稳、故障和回滚报告 |
| V5 生产灰度 | 影子或 canary 的质量、SLO、错误和资源对比 | 灰度结论、审批记录、回滚点 |

V0 至 V2 未通过不得进入大规模性能测试；V4 未通过不得进入生产灰度。

### 5.2 公平比较条件

所有候选必须固定以下变量；无法固定时必须解释差异并禁止直接计算加速比：

- 同一模型 revision、权重 digest、tokenizer/template、前处理和后处理；
- 同一质量门槛、输入集合、顺序或可重放到达过程；
- 同一 shape/输入输出 token 联合分布和最大输出限制；
- 同一硬件型号、数量、拓扑、隔离、功耗模式、驱动和固件；
- 同一服务协议、客户端位置、连接复用、超时和流式消费速度；
- 可比的 batch、并发和 SLO；引擎自行组批时记录实际 batch 分布和等待时间；
- 明确冷缓存/热缓存、prefix cache 命中率、预热前/预热后和首次请求边界；
- 正式测试关闭 profiler，且不得与训练、Notebook 或其他压测共享设备。

公开 benchmark 只用于产生候选，不能替代本项目实测或直接形成容量承诺。

### 5.3 基准矩阵

测试矩阵应覆盖生产分布，而不是穷举任意组合：

| 维度 | 最低覆盖 |
| --- | --- |
| batch | 1、典型在线 batch、离线吞吐 batch |
| shape/长度 | P50、P95、最大允许值、每个主要 bucket/profile |
| 并发 | 1、SLO 容量点、饱和点和过载点 |
| 精度 | 认可基线 + 最多两个目标低精度方案 |
| 缓存 | 冷、生产代表性命中率；热缓存只作为上限 |
| 副本/规模 | 单副本、单节点目标配置、多节点目标规模 |
| 异常 | 错误/越界输入、取消、慢客户端、OOM 边界、进程/节点重启 |

LLM 至少包含短输入短输出、中等真实分布、长 prefill 混合短请求和脱敏生产回放/等价合成流量，
并单独验证 prefix cache、结构化输出、工具调用和请求取消。

### 5.4 计时和统计

1. 分别记录导出/量化时间、engine build 时间、进程到 ready、首请求和预热后稳态。
2. 预热必须覆盖所有 shape bucket/profile，且确认不再发生首次编译；不得丢弃生产中不可避免的
   重编译或 cache miss。
3. 离线 GPU 测试使用设备 event 或在计时边界同步；在线测试以客户端端到端时间为主，并用
   服务 trace 分解排队、前处理、模型和后处理。
4. 正式配置至少执行 3 个相互独立的稳态轮次，报告各轮结果、总体 P50/P95/P99/max、波动或
   95% 置信区间，不能只报告最好一轮或平均值。
5. 声明 P99 达标的单个测试点原则上至少需要 10,000 个符合目标流量模型的请求观测；超时和
   错误不得从总体统计中剔除。不足时必须标记为探索性结果并报告样本数和不确定性。
6. 在线测试每个负载点在预热后至少持续 15 分钟，并同时满足预定样本量；长稳测试的时长由
   服务等级预先确定，在线生产候选不得少于 2 小时。
7. 吞吐搜索从低并发增加到饱和和过载，找出满足全部 SLO 的最大可持续 goodput，而不是只测
   无延迟约束的峰值吞吐。
8. 随机化候选执行顺序，监控温度、频率和后台负载；环境漂移时该轮作废。

### 5.5 指标定义

| 指标 | 统一口径 |
| --- | --- |
| latency | 明确模型执行或客户端端到端边界，在线必须报告 P50/P95/P99/max |
| throughput | samples/s、requests/s 或 tokens/s，必须同时给 batch、并发和输入分布 |
| goodput | 单位时间内成功且满足全部质量、延迟和错误率 SLO 的有效请求或 token 数 |
| speedup | 同一边界下 `基线耗时 / 候选耗时`，同时报告绝对值 |
| relative gain | 同时报相对 B0 的总收益和相对同精度 B1 的引擎增量收益 |
| queue time | 请求到达服务到进入实际执行的时间 |
| memory | 进程 RSS、host 峰值、设备 allocated/reserved/峰值和 OOM 水位 |
| utilization | CPU、GPU、内存带宽、Tensor Core/SM、I/O 和网络；只作瓶颈证据 |
| reliability | error、timeout、OOM、取消泄漏、重启次数和恢复时间 |
| cost | 只以通过质量和 SLO 的 goodput 计算每请求/样本/百万 token 成本 |

LLM 还必须报告 TTFT、ITL、E2E latency、input/output tokens/s、request goodput、KV 使用/抢占/
换出和 prefix cache 命中。TPOT 必须说明公式以及是否排除首 token；不能用总 token 吞吐替代
output throughput，也不能用短输出 requests/s 代表真实容量。

### 5.6 质量验证和数据边界

质量按三层验证：

1. **数值层**：shape、dtype、NaN/Inf、绝对/相对误差、cosine similarity；容差按任务和精度
   预先确定，不使用一个通用 `allclose` 阈值覆盖全部输出。
2. **任务层**：使用项目主指标和正式验证集，例如 accuracy、F1、mAP、WER、NDCG、ROUGE、
   perplexity 或经过定义的人工/模型评审。
3. **业务层**：关键切片、长尾样例、安全规则、工具调用 schema、拒答和回归用例。

生成模型的随机采样不要求逐 token 相同。先用固定 seed/确定性路径定位数值问题，再按任务和
业务分布验收。调参、校准、量化和候选选择只使用训练/验证证据；选定配置后才执行一次正式
测试评估。报告不得泄露敏感输入、秘密标签或受限样本。

### 5.7 稳定性和故障验证

至少验证：

- 持续负载下的内存/KV 增长、allocator 碎片、GC、热降频和尾延迟；
- 超过并发、batch、shape、上下文和显存边界时能限流或明确失败，而不是静默降级；
- 客户端超时/断开能够传播取消并释放计算、队列和 KV Cache；
- 非法输入、损坏制品、依赖超时、进程重启和节点摘除不会发布部分结果；
- 冷节点可加载、预热并进入 ready，故障后在目标时间内恢复；
- 上一完整版本可实际加载并通过 smoke test，回滚不依赖现场重新构建。

若无法安全注入节点故障，必须说明未测范围、替代证据和生产缓解措施。

### 5.8 验收门槛模板

以下空白必须在测试前填写；项目可增加更严格门槛，不得在看到结果后放宽而不重新审批：

```text
基线：B0 Run ID = ______；B1 Run ID = ______；计时边界 = ______；输入点位 = ______
基线性能：B0 P50/P95/P99 = ______；B1 P50/P95/P99 = ______；峰值显存 = ______
相对目标：相对 B0 总加速 >= ______；相对同精度 B1 引擎加速 >= ______；显存降低 >= ______
质量：主指标 ______ [>=|<=] ______，相对基线退化不超过 ______；关键切片全部通过；NaN/Inf = 0
覆盖：目标输入范围 100%；未批准 CPU/eager fallback = 0；持续重编译 = 0
在线：P99 <= ______ ms；goodput >= ______ req/s；error <= ______；timeout <= ______
LLM：TTFT P99 <= ______；ITL P99 <= ______；output goodput >= ______ tok/s
资源：峰值显存 <= ______；RSS <= ______；单节点副本数 >= ______
启动：进程到 ready <= ______ s；首请求 <= ______ s
稳定：连续 ______ h 无泄漏/OOM；取消资源释放 <= ______ s
恢复：进程/节点故障恢复 <= ______ s；上一版本回滚 <= ______ s
成本：每 ______ 请求/样本/token <= ______
统计：每配置独立轮次 >= 3；P99 样本 >= 10,000；环境漂移检查通过
```

## 6. 记录、评审与发布

### 6.1 MLflow 记录

每个候选配置使用独立 MLflow Run，至少记录：

- `params/tags`：源训练 Run、B0/B1 baseline Run、engine 和精确版本、精度、量化 schema、batch、
  并发、shape profile、硬件标识、代码 revision 和容器 digest；
- `metrics`：质量、P50/P95/P99、吞吐、goodput、内存、启动、成本、错误和恢复时间；
- `artifacts`：环境清单、manifest、构建参数、覆盖/fallback、原始聚合数据、质量/性能/故障报告；
- `lineage`：数据或回放 digest、split、前后处理版本、源模型 URI 和候选/父 Run 关系。

只能通过 MLflow Tracking、Artifact 和 Registry API 访问远端系统，不直接查询 `mlflow.db`，
不读取服务端 MinIO 文件系统，也不向客户端分发长期对象存储凭据。分布式任务只由权威 driver
创建/结束父 Run 和发布共享制品，重试不得覆盖已有 Run。

### 6.2 最终决策记录

正式评审至少输出一页结论：

```text
推理契约版本 / 源模型 Run ID / B0 与 B1 Run ID / 数据或回放 digest
候选及被淘汰原因 / 硬门槛结果 / 加权分数
相对 B0 总收益 / 相对同精度 B1 增量收益 / 质量、SLO、goodput、资源、成本和稳定性结果
主方案 / 回滚方案 / 已知风险 / 未测范围
目标硬件和兼容软件集合 / 重建步骤 / 制品 URI
容量假设 / 告警阈值 / 灰度比例 / 回滚触发器
技术负责人 / 模型负责人 / 平台与安全审批
```

### 6.3 发布要求

1. 使用参数化 Ray Job 或等价可恢复脚本完成构建和验证；Notebook 只用于探索和短 smoke。
2. 所有 CPU、GPU、内存和拓扑显式声明，不假设共享集群资源空闲。
3. 服务从不可变制品加载，ready 前完成 digest、自检和代表性 shape 预热。
4. 先做影子或 canary；同时观察质量、P99、错误、资源和回退，不只观察平均延迟。
5. 达到预设门槛并完成显式评审后才修改 Registry alias；自动调优和压测不得自动发布。
6. 回滚使用已审核的完整兼容集合，不在故障现场覆盖 artifact 或临时修改生产模型。

以下变化必须触发相应级别的重新验证：模型/权重、tokenizer 或前后处理、量化格式、PyTorch/
engine/kernel、驱动/固件、GPU/CPU 代际、编译参数、shape profile、服务批处理/并发、容器基础镜像
和安全相关依赖。硬件相关 engine 原则上重新构建，不把历史二进制当作通用源模型。

## 7. 禁止项

- 不用不同 batch、精度、长度、缓存命中或硬件比较并宣称加速比；
- 不把导出、engine 构建或单个样例运行成功等同于生产可用；
- 不静默接受 CPU/eager fallback、shape 越界或持续重编译；
- 不在最终测试集上反复选择量化、编译参数或候选引擎；
- 不用峰值吞吐替代满足 P99、质量和错误率的 goodput；
- 不使用 `latest`、未固定容器或无法从源 Run 重建的生产制品；
- 不把敏感请求、预测、secret 或长期对象存储凭据写入日志和 artifact；
- 新项目不默认采用已归档/停止主动维护的 TorchServe、TGI、IPEX、FasterTransformer、
  AutoGPTQ 或 AutoAWQ；存量系统按风险和契约测试有计划迁移。
